### 为什么后端测试不放在 `src/test`

Maven 默认约定是 `src/test/java`。本工程按要求统一收进根 `tests/`，
因此在 `pom.xml` 显式覆盖：

```xml
<testSourceDirectory>${project.basedir}/../tests/backend/java</testSourceDirectory>
<testResources>
  <testResource><directory>${project.basedir}/../tests/backend/resources</directory></testResource>
</testResources>
```

**代价**：IDE（IDEA/VSCode）需重新导入 Maven 工程才能把该目录识别为测试源码根。
若后续觉得别扭，改回 `src/test/java` 只需删掉这两段配置、移动目录即可，测试代码本身无需改动。

## 二、测试命令

### 后端（在 `petmate-backend/` 下执行）

| 命令 | 作用 |
|---|---|
| `mvnw.cmd test` | **全量测试**（日常用这条）。自动排除 known-issue 分组 |
| `mvnw.cmd test "-Dtest.groups=unit"` | 只跑 L1 单元测试（秒级，无需 Docker） |
| `mvnw.cmd test "-Dtest.groups=integration"` | 只跑 L3-a 集成测试（需 Docker） |
| `mvnw.cmd test "-Dtest.groups=concurrency"` | 只跑 L3-b 并发测试（需 Docker） |
| `mvnw.cmd test "-Dtest.groups=known-issue" "-Dtest.excludedGroups="` | **只看已知缺陷清单**，预期全部失败 |
| `mvnw.cmd test -Dtest=RefundStatusTest` | 跑单个测试类 |

### 前端（在 `frontend/web/` 下执行）

| 命令 | 作用 |
|---|---|
| `npm test` | **全量测试**（日常用这条） |
| `npm run test:watch` | 监听模式，改代码自动重跑 |
| `npm run test:ui` | 浏览器可视化界面 |
| `npm run test:coverage` | 带覆盖率报告 |

## 三、测试报告输出

全部输出到 `项目测试/测试报告/`（已加入 `.gitignore`，属构建产物）。

| 路径 | 内容 | 产生命令 |
|---|---|---|
| `backend/surefire/*.xml` | JUnit XML（CI 消费） | `mvnw.cmd test` |
| `backend/coverage/index.html` | JaCoCo 覆盖率（浏览器打开） | `mvnw.cmd test` |
| `frontend/junit.xml` | JUnit XML | `npm test` |
| `frontend/html/index.html` | Vitest HTML 报告 | `npm test` |
| `frontend/coverage/index.html` | v8 覆盖率 | `npm run test:coverage` |

> **踩坑记录**：JaCoCo 的探针数据文件 `jacoco.exec` 刻意留在 `petmate-backend/target/`
> 而非中文报告目录。因为 `prepare-agent` 会把路径拼进 JVM 的 `-javaagent` 参数，
> Windows 下按 GBK 传递会让中文路径变乱码，导致 agent 写不出文件、报告为空。
> 最终 HTML 报告仍输出到中文目录（那一步走 Java File API，中文正常）。

## 四、后端文件说明

### 4.1 测试基建 `tests/backend/java/com/petmate/support/`

| 文件 | 作用 |
|---|---|
| **`IntegrationTestBase.java`** | L3 集成测试基类。`@SpringBootTest` + Testcontainers MySQL 8.0 + MockMvc。容器为 `static` 且开启 reuse，**全套件共用一个实例**而非每类重启。提供 `url()` helper 自动拼 `/api/v1` 前缀 |
| **`ConcurrencyTestBase.java`** | L3-b 并发测试基类。关键差异：**显式关闭事务托管**（`Propagation.NOT_SUPPORTED`）。因为并发工作线程持有独立 DB 连接，看不见主线程事务里未提交的数据 —— 不关的话造好的商品对工作线程根本不存在。改由 `@AfterEach` 手工清理 |
| **`ConcurrencyHelper.java`** | 并发执行器。用**两道 `CountDownLatch`**（ready + start）做统一发令。不这么做的话线程是陆续启动的，第 1 个任务可能在第 50 个提交前就跑完，压根形成不了竞态，超卖测试永远绿 —— 测了个寂寞 |
| **`TokenFactory.java`** | 各角色 token 签发。复用生产的 `JwtService` 而非自己拼 JWT，保证 claims 结构与真实登录完全同构。覆盖越权矩阵需要的 7 种身份（匿名/用户A/用户B/商家A/商家B/员工CS/管理员），另提供 `tampered()` 构造篡改签名的 token |
| **`TestDataFactory.java`** | 用 SQL 直接造种子数据。**不走接口造数据** —— 否则「前置条件」依赖「被测对象」，注册接口一坏，下单测试也跟着红，故障定位被污染。ID 从 10_000_000 起分配，避开业务数据区间 |
| **`DockerAvailable.java`** | Docker 可用性探测（JUnit `ExecutionCondition`）。**这是本次搭建的关键设计**，见下方 §六 |
| **`RequiresDocker.java`** | 注解，挂在需要 Docker 的测试类上 |

### 4.2 L1 单元测试 `tests/backend/java/com/petmate/unit/`

| 文件 | 被测 | 用例数 | 为什么测它 |
|---|---|---|---|
| **`RefundStatusTest.java`** | `refund/RefundStatus` | 32 | 售后是全项目最复杂逻辑（11 状态 × 3 主线 × 三端驱动，关联 B-S1），且是纯静态方法无 DB 依赖 —— 后端少数「单测性价比极高」的地方 |

| **`CityUtilTest.java`** | `common/CityUtil` | 17 | 同城筛选是 SQL 精确匹配，city 有三个来源三种格式。归一化分叉会导致「同城帖子互相看不见」—— 典型的不报错但静默失效 |

## 五、前端文件说明

### 5.1 配置

| 文件 | 作用 |
|---|---|
| **`frontend/web/vitest.config.ts`** | 独立测试配置。**刻意不写进 `vite.config.ts`** —— 那份配置的 `optimizeDeps.include` 列了 60+ 项且极其脆弱（F-O1：触发 re-optimize 会让 dev server 进程退出、页面全白），测试不该去碰它。只复用 alias 与 vue 插件 |

配置里有三处 Windows 专属处理，都已写在注释里：
1. glob 路径转正斜杠（反斜杠会被当转义符 → "No test files found"）
2. `server.fs.allow` 放行仓库根（测试代码在 Vite root 之外，默认被拒绝加载）
3. 测试依赖显式 alias 到 `frontend/web/node_modules`（`tests/` 目录下没有 node_modules，裸包导入解析不到）

### 5.2 测试基建 `tests/frontend/`

| 文件 | 作用 |
|---|---|
| **`setup/index.ts`** | 全局 setup，每个测试文件前自动加载。四件事：① polyfill `ResizeObserver`/`IntersectionObserver`/`matchMedia`（Element Plus 依赖，jsdom 没有）② 全局注册 Element Plus ③ 托管 MSW 生命周期 ④ 每个用例前清 `sessionStorage`/`localStorage`（token 存 sessionStorage、购物车存 localStorage，不清会让登录态泄漏到下个用例，产生「单跑通过、全跑失败」这类最难查的问题） |
| **`msw/server.ts`** | MSW Node 服务器实例。`onUnhandledRequest: 'error'` —— 未 mock 的请求直接报错而非放行到真实网络，第一时间暴露漏 mock |
| **`msw/handlers.ts`** | 默认 handler，**只放 happy path**。异常场景由具体用例 `server.use()` 就近覆盖 —— 全局默认异常会让用例读起来不知道在测什么。含 `ok()`/`fail()` 包装函数，严格遵循后端 `{code,msg,data,traceId}` 格式（注意 HTTP 状态码恒为 200，这是 B-E1 记录的设计问题） |
| **`fixtures/index.ts`** | 测试固定数据。用例通过展开覆盖关心的字段（`{...cartItem, valid:false}`），好处是只显式声明「与默认值的差异」，读者一眼看出关键变量 |

### 5.3 L1 单元测试 `tests/frontend/unit/utils/`

| 文件 | 被测 | 用例数 | 为什么测它 |
|---|---|---|---|
| **`aiMarkdown.test.ts`** | `utils/aiMarkdown.ts` | 24 | ★ **前端最高优先级**。输出直接进 `v-html`，输入是 LLM 生成的不可信内容，转义有缺口就是实打实的 XSS（F-X1）。含 script/img onerror/svg onload/iframe/引号突破/二次解码绕过等 10 个攻击向量。前端计划 §七 规定：**唯一不接受「预期失败」的一组** |
| **`format.test.ts`** | `utils/format.ts` | 42 | `formatMoney` 收「分」、`formatYuan` 收「元」，两个 API 极像却差 100 倍，而后端返回的是元（F-M3）。用例把单位契约钉死，并专门有一条文档化这个易错点 |

### 5.4 为什么用 MSW 而不是 mock axios

`request.ts` 的拦截器逻辑（错误码映射、401 下线、Idempotency-Key 注入）**本身就是被测对象**。
mock axios 实例等于把被测代码 mock 掉了。MSW 在网络层拦截，真实拦截器能跑起来。

## 六、⚠️ 当前限制与后续工作

### 6.1 本机 Docker 不可用 → L3 集成测试全部跳过

搭建时已探测：本机 Docker daemon 未运行，Testcontainers 无法启动 MySQL 容器。

**处理方式**：集成测试挂 `@RequiresDocker`，Docker 缺失时用例标记为 **skipped 而非 failed**。
理由：这是**环境缺失**不是**代码缺陷**，两者必须在报告里区分开，否则一片红会淹没真正的问题。

当前实际执行结果：

```
后端  Tests run: 65, Failures: 0, Errors: 0, Skipped: 3   BUILD SUCCESS
      └─ 62 条 L1 单元测试通过，3 条 L3 因无 Docker 跳过
前端  Test Files 2 passed, Tests 66 passed
```

启动 Docker Desktop 后重跑，L3 用例即自动参与执行。

### 6.3 本次新发现 6 个缺陷（已用 `known-issue` 固化）

搭建 L1 用例时**实测发现**，均为空值处理缺陷，不在原计划清单内：

| # | 位置 | 问题 | 触发输入 | 建议修复 |
|---|---|---|---|---|
| 1 | `RefundStatus.isValidType()` | 抛 NPE | `null` | `type != null && TYPE_TEXT.containsKey(type)` |
| 2 | `RefundStatus.isFinal()` | 抛 NPE | `null` | `status != null && FINAL_STATUS.contains(status)` |
| 3 | `RefundStatus.statusText()` | 抛 NPE | `null` | 提前 `if (status == null) return ""` |
| 4-6 | `CityUtil.normalize()` | 抛 `ArrayIndexOutOfBoundsException` | `"//"`、`"/"`、`"  /  /  "` | `parts.length == 0` 时返回 null |

**根因（1-3）**：`Map.of()` / `List.of()` 创建的不可变集合，其 `containsKey(null)` /
`contains(null)` / `getOrDefault(null, ...)` 会抛 NPE，而非像 `HashMap` 那样返回 false。
第 3 条尤其隐蔽 —— 源码写的是 `getOrDefault(status, status == null ? "" : status)`，
**看起来处理了 null，实际 getOrDefault 先对 key 做了 requireNonNull，根本走不到 defaultValue**。

**根因（4-6）**：`"//".split("[/\\s]+")` 返回**长度为 0** 的数组（Java 丢弃全部尾部空串），
而代码直接取 `parts[0]`。

**影响**：`CityUtil.normalize()` 在发帖与改资料两个**写入端**被调用，入参直接来自前端 body；
`RefundStatus` 三个方法在售后列表与状态流转中被调用。脏数据或历史 NULL 会让接口抛 500 而非按契约返回。

按两份计划一致的原则 —— **用测试固化缺陷，而不是放宽断言让测试变绿** ——
这些用例断言的是**期望行为**，打了 `@Tag("known-issue")` 默认排除在日常构建外。
修复后应能直接通过，届时移除该 tag 即可。

查看清单：`mvnw.cmd test "-Dtest.groups=known-issue" "-Dtest.excludedGroups="`
