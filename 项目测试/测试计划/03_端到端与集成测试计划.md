## 一、定位与覆盖范围

### 1.1 解决什么问题

| 层级 | 解决的问题 | 本计划解决的事 |
|---|---|---|
| L1 / L2（单测、组件） | 函数、Store、组件逻辑 | — |
| **L3 集成** | 跨类的协作、真实 SQL、并发 | **后端 × 真实 DB；后端 × 后端；前端 × 后端契约** |
| **L4 E2E** | 完整业务流程、跨端协作 | **Playwright 真实浏览器 × 真实后端 × 真实 DB** |

### 1.2 为什么不能省

- 后端架构是 **Service-less**：业务逻辑直接写在 Controller，用 Mock 测等于测 Mock（详见 `01_后端测试计划.md` §1）
- 项目里 **62 张表，DAO/Service/Controller 紧耦合**，单测覆盖几乎无意义，必须用真实 DB 跑 SQL
- 前端 `request.ts` 拦截器的真实拦截逻辑只有 MSW 才能验，而真实 HTTP 链路只有 E2E 能验
- 用户/商家/管理三端涉及的角色切换、菜单权限、支付回跳，必须端到端才能验

## 二、核心场景

> 列出必须端到端跑通的"主流程"。每条流程必须能从一条 SQL DELETE 干净数据库开始跑完。

| 场景 ID | 名称 | 涉及端 | 涉及模块（后端） |
|---|---|---|---|
| **E-S1** | 用户下单 → 支付 → 收货 → 评价 | 全端 | order / payment / product / service / review |
| **E-S2** | 商家发布商品（多 SKU）→ 用户下单 | 全端 | merchant / product / order |
| **E-S3** | 用户退/换货 → 商家审核 → 退款 | 全端 | aftersale / refund / merchant |
| **E-S4** | 商家发布服务（动态规格）→ 用户预约 | 全端 | merchant / service / appointment |
| **E-S5** | 用户发起领养申请 → 商家审核 | 全端 | adoption / merchant |
| **E-S6** | AI 问诊流式问答（SSE） | 用户端 | consult |
| **E-S7** | 商家入驻申请 → 管理端审核 | 商家 + 管理 | merchant / admin |
| **E-S8** | 用户举报内容 → 管理端处置 | 全端 | community / admin |
| **E-S9** | 商家调价 / 改库存的并发下单 | 全端 | order（CAS） / merchant |
| **E-S10** | 支付宝当面付回调验签 | 后端 | payment（独立可脱前端验） |

### 跨模块集成场景（仅后端、不开浏览器）

| 场景 ID | 名称 | 涉及模块 |
|---|---|---|
| **I-M1** | JWT 鉴权链路（签发 → 拦截 → 解析 → ThreadLocal → 清理） | security 全链 |
| **I-M2** | ThreadLocal TokenContext 在异常路径下的清理（含 ControllerAdvice） | security + 全局异常 |
| **I-M3** | 短信验证码的完整生命周期（生成 → 校验 → 失效/过期） | auth |
| **I-M4** | 支付宝回调验签 + 幂等 + 状态机 | payment |
| **I-M5** | 数据权限矩阵：用户/商家/管理三端互不可见 | 全 Controller |
| **I-M6** | Schema 迁移一致性：v1~v16 + seed 全部跑通，库与 dev 环境等价 | sql |

## 三、高风险功能（L3/L4 视角）

### 3.1 并发与一致性

| ID | | 风险 | 触发场景 | 验证 |
|---|---|---|---|---|
| **E-C1** | 🔴 | **CAS 库存扣减竞态**：并发 100 个请求抢同一商品最后 1 件库存。SQL 用 `UPDATE ... WHERE stock >= ?`，必须只 1 个成功，99 个拿到"库存不足"。如果 WHERE 条件漏掉 / 用 `stock=stock-1` 而无乐观锁，**超卖** | I-S1 / E-S1 | Testcontainers 并发线程压；断言 `t_order_item.qty` 之和 ≤ `t_product.stock` |
| **E-C2** | 🟠 | **库存与订单状态机不一致**：下单成功后订单超时未支付回滚库存，回滚过程中用户刚好支付 → 双写。常见病：库存回滚/支付回执是两条独立 update，无事务 | I-S1 | 模拟"超时取消 + 第三方支付成功"并发 |
| **E-C3** | 🟠 | **优惠券/积分余额超扣**：并发使用同一张券/同一组积分。当前代码用 `UPDATE t_user_coupon SET status=1 WHERE status=0` 应可锁；用 `SELECT ... status=0` 后 `UPDATE` 必超扣 | I-M5 | 并发抢同一券，断言**有且仅有 1 个成功**，其余 20001 |
| **E-C4** | 🟠 | **商家改库存与下单竞态**：商家把库存从 10 改为 0 同时用户正在结算页提交 —— 必须至少一方明确失败 | E-S9 | Testcontainers 双线程 |
| **E-C5** | 🟡 | **SSE 连接断连**：AI 问诊中途断网，重连后上下文丢失 / 重复发送 | E-S6 | 客户端 abort 后重连，断言服务端 message 序号连续无重复 |

### 3.2 支付链路

| ID | | 风险 | 验证 |
|---|---|---|---|
| **E-P1** | 🔴 | **支付宝回调验签**：项目用 RSA2 (SHA256withRSA)，验签失败的请求必须拒绝。当前 `AlipayNotifier` 用 `AlipaySignature.rsaCheck()`，需**篡改金额、订单号、时间戳三种字段**分别验拒 | I-M4 |
| **E-P2** | 🔴 | **支付回调幂等**：同一通知可能发多次（支付宝文档明确保证"至少一次"），后端必须能去重。当前实现用 `t_payment_log` + 唯一索引 —— 断言**重复通知处理后业务表状态不变、日志只有 1 条 `success`** | I-M4 |
| **E-P3** | 🟠 | **支付金额篡改**：客户端传 `payAmount` 与后端订单金额不一致时，必须以后端为准。当前 `OrderController.pay()` 接收 `payAmount`，**有可能是从前端传的，必须验** | E-S1 |
| **E-P4** | 🟠 | **支付回跳路径**：`return_url` 路径受前端守卫驱动，参数缺失/篡改时必须降级而非崩 | F-G4 |

### 3.3 鉴权 / 数据权限

| ID | | 风险 | 验证 |
|---|---|---|---|
| **E-A1** | 🟠 | **IDOR（Insecure Direct Object Reference）**：用户 A 用自己的 token 请求 `/order/detail/{id_B}` 必须 403/404 | I-M5 |
| **E-A2** | 🟠 | **跨商家越权**：商家 A 用 token 请求商家 B 的商品改价/订单审核 | I-M5 |
| **E-A3** | 🟠 | **跨端越权**：用户 token 命中 `/admin/**` 必须 403，不是 200 + 错误数据 | I-M5 |
| **E-A4** | 🟡 | **注销 token 仍可用 7 天**：登出只清前端 sessionStorage，**后端 JWT 无黑名单、无吊销接口**。后端只在 `JwtAuthFilter` 里查 `t_user.status`，被封禁用户仍可访问**非鉴权接口**（如商品列表），但需登录接口会拒 | I-M1 / I-M5 |
| **E-A5** | 🟡 | **商家/管理封禁失效**（已在后端计划 B-A4）：`requireRole()` 不查 ban，`requireRoleAndActive()` 0 个调用者 | I-M5 |

### 3.4 端到端 UX

| ID | | 风险 | 验证 |
|---|---|---|---|
| **E-U1** | 🟠 | **支付成功回跳白屏**：守卫 `?payType=` 解析失败 → 卡死 | F-G4 |
| **E-U2** | 🟠 | **登录态跨标签页不一致**：sessionStorage 关闭即清（详见 F-A1） | F-A1 |
| **E-U3** | 🟠 | **新引入 Element Plus 组件未列入 optimizeDeps**：dev server 退出、页面全白（F-O1） | — |
| **E-U4** | 🟡 | **图片懒加载失败**：超长 base64 头像/问诊图（后端 LONGTEXT）首屏卡死 | F-X4 |
| **E-U5** | 🟡 | **ECharts 在容器未渲染时初始化** → 0 尺寸图表（F-O4） | — |

### 3.5 配置 / 环境

| ID | | 风险 | 验证 |
|---|---|---|---|
| **E-N1** | 🔴 | **`schema.sql` 缺 7 类表，`reset_and_seed.sh` 不跑 v2~v16**：任何自动化测试都拿不到与 dev 等价的库 | I-M6（**P0 阻塞所有 L3/L4**） |

## 四、测试分层方案（L3/L4）

### 4.1 L3-a 真实库单 Controller 集成（Spring Boot Test + Testcontainers）

**目标**：在不启动 HTTP 监听的前提下，把 Controller 的实际方法跑在真实 MySQL 上。

**栈**：
```
JUnit 5 + Spring Boot Test（@SpringBootTest, webEnvironment = NONE）
+ Testcontainers MySQL 8.0（reuse=true）
+ WireMock（mock 支付宝 / 短信网关）
+ AssertJ
```

**典型骨架**：
```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.NONE,
                properties = {
                  "spring.datasource.url=${TC_MYSQL_URL}",
                  "petmate.alipay.enabled=false"
                })
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
class OrderControllerIT {

  @Container static MySQLContainer<?> MYSQL = new MySQLContainer<>("mysql:8.0")
      .withDatabaseName("petmate").withUsername("test").withPassword("test");
  @Autowired OrderController orderController;
  @Autowired JdbcTemplate jdbc;
  @Autowired MockBean SmsService sms;

  @BeforeEach void seed() {
    jdbc.execute("DELETE FROM t_order_item");
    jdbc.execute("DELETE FROM t_order");
    // 重置库存
  }

  @Test void 下单成功路径() { ... }
  @Test void 并发抢同一商品最后1件库存_只一个成功() {
    // 50 线程并发
    // 断言 1 个 order status=CREATED，49 个 BizException(stock)
    // 断言 t_product.stock >= 0
  }
}
```

**关键要求**：
- 不再依赖 `src/main/resources/schema.sql`，而是 **`schema_full.sql`**（见 §6.1）
- 每条用例前用 `DELETE` + 种子脚本恢复到 known state；**不要用 `@Transactional` 回滚**，因为本项目**默认 autoCommit=true 大量手写 SQL，回滚行为不可控**

### 4.2 L3-b 端到端 HTTP（Spring Boot Test + MockMvc + Testcontainers）

**目标**：完整走 `DispatcherServlet` → `JwtAuthFilter` → Controller → DB。

**栈**：MockMvc（start-up 后切到 `RANDOM_PORT` 也可；前者更快）。

```java
@SpringBootTest @AutoConfigureMockMvc
@Testcontainers
class OrderPayFlowIT {
  @Autowired MockMvc mvc;
  @Container static MySQLContainer<?> MYSQL = ...;
  // WireMock 拦截支付宝网关
  static WireMockServer WMS = new WireMockServer(8089);
  @BeforeAll void startWM() { WMS.start(); }
}
```

适用：JWT 链路、支付宝回调幂等、跨端鉴权矩阵（I-M1/I-M4/I-M5）。

### 4.3 L3-c 契约（前端 MSW handlers ↔ 后端接口）

**目标**：前端用 MSW mock 出后端真实响应形状，验证前端代码对接口契约的理解；后端则用 `springdoc` / 文档/示例响应反查。

**做法**：
- 在 `frontend/web/src/test/msw/handlers.ts` 中**只放符合 OpenAPI/实际响应的 mock**，故意"忘写字段"或"字段类型错"应让前端断言失败 → 这就是契约回归
- 关键接口清单：`/auth/sms/send`、`/auth/login`、`/order/create`、`/order/pay`、`/aftersale/create`、`/community/post/upload`、`/payment/alipay/notify`

### 4.4 L4 E2E（Playwright + 真实后端 + 真实 DB）

**目标**：用户视角跑通主流程。

**栈**：
```
@playwright/test  （建议从 raw playwright-core 迁过来 —— 见 §6.4）
backend-testcontainer 或本地 MySQL（用 reset_and_seed.sh + v2~v16）
npm run dev（前端）→ :5173
```

**`playwright.config.ts`**：
- `baseURL: http://localhost:5173`
- `webServer: [{ command: 'cd ../petmate-backend && mvn spring-boot:run', port: 8080, reuseExistingServer: !process.env.CI, timeout: 120_000 }, { command: 'npm run dev', port: 5173, reuseExistingServer: !process.env.CI, timeout: 60_000 }]`
- `projects: [chromium, firefox, webkit]`（只跑 chromium 也行，按 CI 资源决定）
- `use: { trace: 'on-first-retry', screenshot: 'only-on-failure', video: 'retain-on-failure' }`

**目录**：
```
e2e/
├── fixtures/
│   ├── auth.ts          # 各端登录 helper（用 demo 账号 + 短信码 123456）
│   └── api.ts           # 直接用后端 API 准备数据（如先创建一个商家后台再 UI 验证）
├── flows/
│   ├── checkout.spec.ts
│   ├── aftersale.spec.ts
│   └── alipay-return.spec.ts
└── helpers/
    └── reset-db.ts      # 调 reset_and_seed.sh 入口（要求 dev 库可丢）
```

### L3-b HTTP 链路（~12 条）

| 场景 | 关联 ID |
|---|---|
| JWT 签发 → 拦截 → ThreadLocal → 异常路径清理 | **I-M1** / **I-M2** |
| JWT 被篡改（改 payload / 改签名）→ 401 | I-M1 |
| Token 过期 → 401 + traceId 正确 | I-M1 |
| 用户被禁用（status=0） → 401/403 | E-A4 |
| **商家被禁用** → `/merchant/**` 仍可访问（暴露 B-A4） | **E-A5** |

| 用户 A 请求用户 B 的订单 → 403/404 | **E-A1** |
| 商家 A 请求商家 B 的商品改价 → 403 | **E-A2** |
| 用户 token 请求 `/admin/**` → 403 | **E-A3** |
| `traceId` 在响应头/响应体正确贯穿 | — |

### L4 E2E（~10 条）

| Flow | 步骤（Playwright） | 关联 ID |
|---|---|---|
| **用户下单 + 支付宝沙箱支付成功回跳** | 登录 → 商品详情 → 加购 → 结算 → 提交订单 → 唤起支付（mock）→ 模拟支付宝 return_url → 跳订单详情显示已支付 | E-S1 / E-P4 |
| **商家改库存后用户结算拦截** | 商家后台改库存为 0 → 用户在结算页点提交 → 收到"库存不足"提示，订单未创建 | E-C4 / E-S9 |
| **退换货完整流** | 用户下单 → 支付 → 申请退货 → 商家审核同意 → 用户上传凭证 → 商家确认收款 → 状态完成 | E-S3 |
| **领养申请 + 商家审核** | 用户提交申请 → 商家后台审核 → 用户看到状态更新 | E-S5 |
| **AI 问诊流式输出** | 用户输入 → 看到字符逐字出现 → 异常字符被 `cleanConsultText` 剥离 → 最终完整渲染（含免责声明） | E-S6 / F-X1 |
| **管理端封禁商家后商家端登出** | 管理端禁用商家 → 商家端下一次操作弹出 20001 → 跳登录 | E-A5 |
| **登录态跨标签页** | 标签页 A 登录 → 开标签页 B → B 自动登录；A 关闭 → B 不应被踢 | F-A1 / E-U2 |
| **视口守卫** | 浏览器窗口缩到 1023×800 访问 `/admin/*` → 跳 unsupported 页 | F-G2 / E-U3 |
| **支付回跳路径异常** | 直接访问 `/user/vip/result/xxx?payType=vip`（缺订单号）→ 优雅降级而非白屏 | E-U1 |
| **新组件引入 → dev server 退出** | （人工 smoke，自动化难复现沙箱）→ 流程跑通前必须先补 optimizeDeps | E-U3 |
