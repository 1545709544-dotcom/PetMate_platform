## 一、项目现状盘点

### 1.1 两个项目的基本盘

| 项目 | 位置 | 技术栈 | 规模 |
|---|---|---|---|
| **petmate-backend** | `D:\PetMate\petmate-backend` | Spring Boot 3.3.5 + JDK 21 + Spring JDBC（手写 SQL）+ MySQL 8 + Redis + jjwt 0.12.6 + BCrypt | 77 个 Java 文件 / **17,363 行** / 32 个 Controller / **292 个接口** |
| **frontend/web** | `D:\PetMate\frontend\web` | Vue 3.5 + TypeScript 5.6 + Vite 5.4 + Element Plus 2.14 + Pinia 2.3 + Vue Router 4 + Axios + ECharts 6 | 234 个源文件 / **116 个 .vue** / **106 条路由** / 16 个 API 模块 / 5 个 Store |

前端三端拆分：用户端 53 页 / 商家端 23 页 / 管理端 24 页。

### 1.2 数据库

- MySQL 8.0，库名 `petmate`，utf8mb4_unicode_ci
- **实际库中有 62 张表**，按业务域分：用户(5) / 宠物(5) / 商品(4) / 交易订单(5) / 支付营销(5) / 商家服务预约(7) / AI问诊(2) / 社区内容(7) / 领养秒杀(3) / 管理风控配置(7) / Banner公告(2) 等
- 金额统一 `DECIMAL(10,2)`；评分有 `DECIMAL(3,2)` 与 `DECIMAL(2,1)` 两种精度（**不一致，需在测试中固化断言**）

### 1.3 现有测试资产（关键结论：基本为零）

| 层次 | 现状 |
|---|---|
| 后端单元测试 | ❌ **`src/test` 目录根本不存在**，零 JUnit 用例（pom 里有 `spring-boot-starter-test` 但未使用） |
| 前端单元测试 | ❌ 零。无 vitest/jest 依赖，无任何 `*.spec.ts` / `*.test.ts`，`package.json` 无 test 脚本 |
| E2E | ⚠️ `D:\PetMate\e2e` 有 **17 个 Playwright-core 手写 .mjs 调试脚本**，但：无统一 runner、无断言框架、`npm test` 是 `echo error`、依赖本地已启动的后端、多为一次性截图排查脚本。**不能算测试资产，只能算调试痕迹** |
| 数据验收 | ✅ `.workbuddy/memory/acceptance_report.md` 有一份领养/商品数据验收报告（人工） |

**结论：这是一个 17k 行后端 + 116 页前端、零自动化测试覆盖的项目。测试建设从 0 开始。**

## 二、启动方式（测试环境前置）

### 2.1 后端

```bash
cd D:\PetMate\petmate-backend
mvnw.cmd spring-boot:run          # Windows
./mvnw spring-boot:run            # Linux/macOS
```

- 端口 `8080`，**context-path = `/api/v1`**（所有接口都带此前缀，易踩坑）
- 配置：`src/main/resources/application.yml`
- 私密配置从仓库外的 `petmate-local.yml` 与 `.env` 注入（含 `ZHIPU_API_KEY`、`ALIPAY_*`）

**已有的多套启动脚本（对测试很有价值，可直接复用为不同测试档位）：**

| 脚本 | 端口 | 档位 | 测试用途 |
|---|---|---|---|
| `start-backend.bat` | 8080 | `ALIPAY_ENABLED=true` 真实支付宝沙箱 | 支付真链路验证 |
| `start-backend-test-demo.bat` | 8081 | `ALIPAY_ENABLED=false` 演示态 | **主力功能回归**（支付直接置 paid，不依赖外网） |
| `start-backend-test-bypass.bat` | 8082 | 真实支付路径但 `ALIPAY_PUBLIC_KEY` 留空 → **跳过验签** | 回调链路验证（沙箱不稳时） |
| `test_env.bat` | — | 仅自检 `.env` 是否被解析 | 环境排障 |

> 坑：批处理 `set` 的环境变量不会传给 java.exe，所有 .bat 都用 `-Dxxx=` 系统属性传递。

### 2.2 前端

```bash
cd D:\PetMate\frontend\web
npm install --legacy-peer-deps
npm run dev          # 端口 5173
```

- Vite 代理：`/api/*` → `http://localhost:8080`；`/static/*` → `http://localhost:8080/api/v1/static/*`
- `vite.config.ts` 的 `optimizeDeps.include` 列了 60+ 项，注释明确说明**运行期二次预构建会导致 dev server 进程直接退出**（沙箱批量删除守卫）。新增 el-* 组件必须补进列表 —— 这是一个已知的环境脆弱点，需写入测试环境文档。

### 2.3 数据库初始化 ⚠️ 阻塞项

```bash
cd D:\PetMate\petmate-backend\sql
./reset_and_seed.sh     # 只跑 schema.sql + seed.sql
```

**严重问题（必须在测试开工前解决）：**

`reset_and_seed.sh` 只执行 `schema.sql` + `seed.sql`，**不执行 v2~v16 的 16 个增量迁移**。而 `schema.sql` 是历史快照，经实际验证**缺失以下 7 类关键表**：

| 缺失表 | 来自迁移 | 影响的业务 |
|---|---|---|
| `t_payment_log` / `t_sms_log` / `t_event` | v2 | 支付对账、短信、埋点漏斗 |
| `t_order.expire_at` 列 | v3 | 订单超时关单 |
| `t_merchant_apply` | v4~v6 | 商家入驻审核 |
| `t_store.status` 列 | v7 | 商家封禁 |
| `t_refund` / `t_refund_log` | v8 | **整个售后 11 态状态机** |
| `t_user_notification` | v9 | 消息中心 |
| `t_pet_reminder` | v12 | 宠物关怀提醒 |
| `t_service_spec` / `t_service_addon` / `t_service_review` | v13 | 服务规格/加购/评价 |
| `t_post.city` 列 | v14 | 社区同城 |

> **用 `reset_and_seed.sh` 建出来的库跑不起来当前后端。** 现有的 62 张表是长期手工叠加迁移的结果，无法复现。
>
> **P0 前置任务**：产出一个 `schema_full.sql`（schema + v2~v16 有序合并），或改造 `reset_and_seed.sh` 链式执行全部迁移，并验证「全新库 → 后端启动 → 冒烟通过」。**没有可复现的测试库，一切自动化测试无从谈起。**

## 四、高风险功能清单（跨项目汇总）

按「出问题的影响 × 出问题的概率」排序。详细验证方案见各项目计划。

### R1 · 资金与库存一致性 【致命】

| ID | 风险 | 位置 | 说明 |
|---|---|---|---|
| R1.1 | **积分并发丢更新** | `points/PointsService.java:82,105,203,245` | `SELECT balance` → 应用层算 → `UPDATE balance = balance + ?`，**无 CAS 无行锁**。并发下 `balance_after` 日志失真；`redeem` 理论可超扣为负 |
| R1.2 | **积分每日上限可突破** | `PointsService` `dailyEarned()` | 事务内 `SELECT SUM` 后判断，并发各读旧值，可突破每日 50 上限 |

| ID | 风险 | 位置 | 说明 |

## 五、测试分层方案

采用**测试金字塔 + 风险驱动**的混合策略。鉴于项目「零测试基础 + 手写 SQL 无 Service 层 + 交付期有限」的特点，做如下调整：

```
                    ╱╲
                   ╱E2E╲          L4  端到端  ~25 条关键路径      Playwright
                  ╱──────╲
                 ╱ 集成测试 ╲       L3  API 集成 ~120 用例         @SpringBootTest + Testcontainers
                ╱────────────╲
               ╱   组件测试    ╲     L2  前端组件/Store ~60 用例    Vitest + @vue/test-utils
              ╱────────────────╲
             ╱     单元测试      ╱    L1  纯函数 ~80 用例           JUnit5 / Vitest
            ╱──────────────────╱
```

### 5.1 为什么不是标准金字塔？

后端 **29/32 的 Controller 直接注入 `JdbcTemplate`，几乎没有 Service 层**（仅 14 个 @Service，且多为工具类）。业务逻辑与 SQL 强耦合写在 Controller 里，**无法用 Mock 做有意义的单元测试** —— 强行 mock JdbcTemplate 只是在测试 mock 本身。

**因此后端重心放在 L3 集成测试层**（真实 DB + 真实 SQL），单元测试只覆盖少数纯逻辑类（`RefundStatus`、`SensitiveWordService`、`JwtService`、`PromptBuilder`、`CityUtil`）。这是对现有架构的务实妥协，而非最佳实践 —— 若未来重构出 Service 层，可回补 L1。

### 5.2 四层职责划分

| 层 | 目标 | 技术选型 | 依赖 | 数量 | 执行时机 |
|---|---|---|---|---|---|
| **L1 单元** | 纯函数、状态机规则、格式化、工具类 | 后端 JUnit5 + AssertJ；前端 Vitest | 无外部依赖 | 后端 ~35 / 前端 ~45 | 每次提交，秒级 |
| **L2 组件** | Vue 组件渲染、Store actions/getters、路由守卫、请求拦截器 | Vitest + @vue/test-utils + MSW（mock 接口） | mock HTTP | ~60 | 每次提交，30s 内 |
| **L3 集成** | 真实 HTTP 打到 Controller → 真实 SQL → 真实 MySQL，验证业务链路、事务、并发、越权 | `@SpringBootTest(webEnvironment=RANDOM_PORT)` + MockMvc/TestRestTemplate + **Testcontainers MySQL** | 真实 DB | ~120 | 每日 / MR，分钟级 |
| **L4 端到端** | 前后端联调、跨端协作流程、UI 关键路径 | Playwright（升级现有 e2e） | 全栈启动 | ~25 | 每日 / 发版前 |

### 5.3 分层归属决策表

| 待测内容 | 归属层 | 理由 |
|---|---|---|
| 售后 11 态合法跃迁规则 | L1 | `RefundStatus` 是纯常量+集合，可纯函数测 |
| 售后跨 3 角色完整流转 | L3 | 需真实 DB 状态与事务 |
| 库存 CAS 防超卖 | L3 | 必须并发打真实 DB |
| 积分并发丢更新 | L3 | 同上 |
| 支付宝验签 | L1 + L3 | 签名算法 L1；回调幂等/金额校验 L3 |
| 越权（改他人订单） | L3 | 必须真实 token + 真实数据归属 |
| `formatMoney` / `regionToCity` | L1 | 纯函数 |
| cart store getters | L2 | 纯计算，mock 数据即可 |
| 路由守卫四重门禁 | L2 | mock router + store |
| axios 401 强制下线 | L2 | MSW mock 响应 |
| 下单→支付→收货全流程 | L4 | 跨前后端 |
| 商家发货→用户确认 | L4 | 跨端协作 |

## 七、优先级与实施路线

### P0 · 先决条件（1~2 天，不做完后面全是空中楼阁）
1. **修复 schema 可复现性**：产出 `schema_full.sql`，验证「全新库 → 后端启动 → 冒烟通过」
2. 搭后端测试骨架：建 `src/test`、引入 Testcontainers + AssertJ、跑通 1 条 hello 用例
3. 搭前端测试骨架：引入 Vitest + @vue/test-utils + MSW、加 `npm run test` 脚本、跑通 1 条用例
4. E2E 骨架：`@playwright/test` 替换裸 `playwright-core`，把 17 个 .mjs 中有价值的改造为标准用例

### P1 · 资金与权限（3~5 天）
覆盖 R1（资金一致性）、R2（支付安全）、R3（越权）、R4（状态机）—— 即所有「致命/高」风险

### P2 · 主流程回归（3~4 天）
下单/售后/预约/社区/问诊主链路 L3 + L4

### P3 · 广度补齐（持续）
管理端、商家端 CRUD、前端组件、边界与异常

### 覆盖率目标（务实，非硬指标）

| 指标 | 目标 | 说明 |
|---|---|---|
| 后端高风险模块（order/pay/refund/security/points）行覆盖 | ≥ 70% | 重点保障 |
| 后端整体行覆盖 | ≥ 40% | 大量 CRUD 样板不强求 |
| 前端 utils + stores 覆盖 | ≥ 80% | 纯逻辑，成本低收益高 |
| 前端整体 | ≥ 30% | 页面组件不追求 |
| **P0/P1 风险点用例覆盖** | **100%** | **这是真正的验收标准** |

> 覆盖率是参考指标，不是目标。**验收标准是「§四 高风险清单每一项都有对应用例并通过」**。

## 九、已知约束与风险

1. **无 CI**：项目无 GitHub Actions / Jenkins 配置，测试只能本地跑。建议后续补 CI，否则测试会迅速腐化。
2. **Windows 本地环境**：Testcontainers 需要 Docker Desktop；若不可用，退化方案是用独立 MySQL 测试库 + 每次 `DROP/CREATE`（隔离性差但可行）。
3. **外部依赖**：智谱 GLM（AI 问诊）、支付宝沙箱、腾讯云短信。测试默认全部走降级/演示态，仅支付专项走真实沙箱。
4. **无 Service 层**导致后端单测价值有限，已在 §5.1 说明取舍。
5. 本计划基于 2026-08-07 的代码静态分析，风险点均标注了文件+行号，**编码前应逐条复核**（代码可能已变动）。
6. **已独立验证的致命缺陷清单**（每条都有专用用例覆盖，但**用例失败本身就是预期**，不阻塞上线但需修复跟进）：
