### 1.4 ⚠️ 架构特征（决定测试策略）

1. **无 Service 层**：29/32 的 Controller 直接注入 `JdbcTemplate`，业务逻辑 + SQL 全写在 Controller 方法里。14 个 `@Service` 多为工具类（Sms/Audit/Notify/SensitiveWord/Points/Idempotency…）。
   → **无法做有意义的 Mock 单元测试**，必须以真实 DB 的集成测试为主。

2. **无统一鉴权层**：`JwtAuthFilter` 只解析 token 写 ThreadLocal，**不做任何拦截，一律放行**。鉴权 100% 靠每个 Controller 手写 `TokenContext.requireXxx()`。
   → **漏写一行 = 一个越权漏洞**，必须逐接口验证。

3. **事务分布**：41 处 `@Transactional`，分布在 14 个类。存在跨事务的资金操作（见 R1.3）。

## 四、测试分层方案（后端）

### 4.1 分层与选型

| 层 | 目标 | 选型 | 数量 | 时长 |
|---|---|---|---|---|
| **L1 单元** | 纯逻辑类，无 DB 依赖 | JUnit 5 + AssertJ + Mockito | ~35 | < 10s |
| **L3-a 集成·切片** | 单接口 × 真实 SQL × 真实 DB | `@SpringBootTest` + MockMvc + Testcontainers MySQL | ~85 | 分钟级 |
| **L3-b 集成·并发** | 资金/库存并发正确性 | 同上 + `ExecutorService`/`CountDownLatch` | ~12 | 分钟级 |
| **L3-c 集成·越权矩阵** | 鉴权与归属校验的系统性覆盖 | 同上 + 参数化测试 | ~25 | 分钟级 |

> 跨前后端的 L4 端到端见 `03_端到端与集成测试计划.md`。

### 4.2 为什么后端不做大量 Mock 单测

如 §1.4 所述，业务逻辑与 SQL 耦合在 Controller 里。Mock `JdbcTemplate` 意味着要 stub 出 `queryForList` 的返回值 —— 那测的是 stub，不是业务。**真正的业务规则（CAS 是否生效、事务是否回滚、状态跃迁是否被 DB 约束）只有真实 DB 能验证。**

因此后端重心在 L3。这是对现有架构的务实妥协；若未来抽出 Service 层，可回补 L1。

#### 售后 11 态（15）
三种 `refund_type` 各自的完整正向链路：
- `REFUND_ONLY`: pending → refunded
- `RETURN_REFUND`: pending → returning → returned → refunded
- `EXCHANGE`: pending → exchanging → returned → reshipped → exchanged

分支：驳回 → rejected → 申请介入 appealing → 平台仲裁 arbitrated；用户撤销 → closed。
校验：每步 `t_refund_log` 流水完整、退款金额不可超订单实付、终态不可再流转、跨角色权限（用户不能调商家接口）

#### 积分（8）
earn/redeem/refund 正常路径、每日上限、余额不足、抵扣计算、日志 `balance_after` 正确性、订单取消后积分回退

#### 商品/秒杀（8）

管理：用户封禁、商家审核、帖子审核、敏感词 CRUD、紧急熔断开关生效、操作日志落库
