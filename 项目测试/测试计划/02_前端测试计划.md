### 1.4 ⚠️ 已知环境脆弱点

`vite.config.ts` 的 `optimizeDeps.include` 有一大段注释说明：Vite 运行期若发现新依赖会触发 re-optimize，需删除临时目录 `node_modules/.vite/deps_temp_xxx`；本机开发沙箱对批量删除（>50 文件）有守卫会拦截，导致 **dev server 进程当场退出、页面全白**。

因此所有可能用到的 element-plus 子组件样式都必须提前列进 include（当前 60+ 项）。

**对测试的影响**：
- 新增 el-* 组件后若忘记补 include，E2E 会以"页面全白"的形式失败，且原因极具误导性
- 测试环境文档必须写明这一点
- 建议增加一条 CI/本地检查：`npm run dev` 启动后扫描日志中是否出现 `new dependencies optimized`

## 三、高风险功能（前端）

> 标记：🔴 致命 / 🟠 高 / 🟡 中

### 3.1 登录态与安全

| ID | | 风险 | 位置 | 验证要点 |
|---|---|---|---|---|
| **F-A1** | 🟠 | **token 存 sessionStorage** → 关闭标签页即登出，多标签页不共享。这是有意设计还是疏漏需确认；对用户体验影响大 | `utils/auth.ts`、`stores/user.ts` | 多标签页/刷新/新开窗口的登录态行为 |
| **F-A2** | 🟠 | **`whenReady()` 时序竞争**：刷新页面时守卫 `await userStore.whenReady()`，若 `fetchUser()` 慢或失败，角色未就绪就放行 → 可能闪现无权限页面 | `stores/user.ts`、`router/guard.ts` | mock 慢响应/失败响应，验证守卫行为 |
| **F-A3** | 🟠 | **角色前端可篡改**：`normalizeRole()` 归一后存于内存，**前端守卫仅是体验层**。真正防线在后端（见后端计划 §3.4）。需确认：改内存中的 role 能否进入管理端 UI（即使接口会拒） | `stores/user.ts` | 手工改 store 中 role 观察路由行为 |
| **F-A4** | 🟡 | `types/common.ts` 的 `UserRole` 含 `guest/vip`，而 `stores/user.ts` 重新声明的只有 `admin/merchant/user`，**两处类型不一致** | 两文件 | 类型断言测试 |
| **F-A5** | 🟡 | 401 处理用 `window.location.href = '/login'` 硬跳转，会丢失当前路径（无 redirect 参数），而守卫的登录门禁却带了 redirect —— **两条路径行为不一致** | `api/request.ts` | 对比两种未登录场景的跳转结果 |

### 3.2 金额与业务计算

| ID | | 风险 | 位置 | 验证要点 |
|---|---|---|---|---|
| **F-M1** | 🟠 | **前端金额计算与后端可能不一致**：cart store 用 `price * quantity` 浮点累加，后端用 `DECIMAL(10,2)`。前端展示金额 ≠ 后端结算金额时用户会投诉 | `stores/cart.ts` `totalAmount` | 构造浮点边界（0.1+0.2、19.99×3），与后端结果比对 |
| **F-M2** | 🟠 | 结算页多重优惠叠加：优惠券 + 积分抵扣 + 运费 + 捐助，**前端预览金额必须与后端最终一致** | `CheckoutView.vue` | 各种组合的金额断言 |
| **F-M3** | 🟡 | `formatMoney(fen)` 接受**分**，`formatYuan(yuan)` 接受**元** —— 两个相似 API 极易调错，且后端返回的是元（DECIMAL） | `utils/format.ts` | 全项目扫描调用点，确认单位正确 |
| **F-M4** | 🟡 | 失效商品(`valid=false`)必须排除出结算，否则下单会被后端拒 | `stores/cart.ts` | 含失效商品的购物车结算 |

### 3.3 请求层

| ID | | 风险 | 位置 |
|---|---|---|---|
| **F-R1** | 🟠 | **Idempotency-Key 每次请求都新生成** `${Date.now()}-${random}` → **实际上防不住重复提交**（两次点击生成两个不同 key，后端视为两次独立请求）。这是一个语义错误的实现 | `api/request.ts` |
| **F-R2** | 🟠 | **无请求重试、无请求取消、无防抖节流** → 弱网下用户连点会产生多个并发请求 | `api/request.ts` |
| **F-R3** | 🟡 | 业务错误码 20001/20003 与 HTTP 401 是**两条独立的下线路径**，逻辑重复且行为不同（见 F-A5） | `api/request.ts` |
| **F-R4** | 🟡 | `__handled` 标记约定：业务层需检查此标记避免二次弹窗，**属口头约定无强制**，新代码易漏 | `api/request.ts` |
| **F-R5** | 🟡 | 后端所有错误都返回 HTTP 200（后端 B-E1），前端完全依赖 body 的 code 字段。若后端返回非预期格式（如网关返回 HTML），解析会崩 | `api/request.ts` |

| ID | | 风险 | 位置 |

| **F-G1** | 🟠 | 守卫六段串行逻辑复杂：支付回跳 → 视口 → whenReady → 登录 → 实名 → 角色。**任一段 return 错误会导致死循环或白屏** | `router/guard.ts` |

## 四、测试分层方案（前端）

### 4.1 分层与选型

| 层 | 目标 | 选型 | 数量 | 时长 |
|---|---|---|---|---|
| **L1 单元** | 纯函数：格式化、地区、markdown、storage | **Vitest**（jsdom 环境） | ~45 | < 5s |
| **L2-a 组件** | Store actions/getters、composables | Vitest + `@pinia/testing` | ~30 | < 15s |
| **L2-b 组件** | Vue 组件渲染与交互 | Vitest + `@vue/test-utils` + **MSW**（mock 接口） | ~25 | < 30s |
| **L2-c 集成** | 请求拦截器、路由守卫 | Vitest + MSW + memory router | ~15 | < 10s |

> 真实浏览器 + 真实后端的 L4 见 `03_端到端与集成测试计划.md`。

### 4.2 为什么用 MSW 而不是 mock axios

`request.ts` 的拦截器逻辑（错误码映射、401 下线、Idempotency-Key 注入）**本身就是被测对象**。若 mock axios 实例，等于把被测代码 mock 掉了。MSW 在网络层拦截，能让真实的拦截器逻辑跑起来，测试价值高得多。

### 4.3 测试基础设施

**依赖（`devDependencies`）：**
```
vitest
@vitest/coverage-v8
@vitest/ui                    （可选）
@vue/test-utils
@pinia/testing
jsdom
msw
```

**`package.json` 新增 scripts：**
```json
"test": "vitest run",
"test:watch": "vitest",
"test:ui": "vitest --ui",
"test:coverage": "vitest run --coverage"
```

**`vitest.config.ts`**（独立文件，避免污染 `vite.config.ts` 的 optimizeDeps）：
- `environment: 'jsdom'`
- `globals: true`
- `setupFiles: ['./src/test/setup.ts']`
- 复用 `vite.config.ts` 的 `resolve.alias`（`@` → `src`）
- coverage：`provider: 'v8'`，`exclude` 掉 `views/**`（页面组件不追求覆盖）

**目录约定：**
```
src/
├── test/
│   ├── setup.ts              # Element Plus 全局注册、ResizeObserver polyfill、sessionStorage mock
│   ├── msw/
│   │   ├── server.ts         # setupServer
│   │   └── handlers.ts       # 各接口的 mock 响应（含错误码场景）
│   └── fixtures/             # 测试数据（购物车/订单/用户）
├── utils/__tests__/
├── stores/__tests__/
├── api/__tests__/
├── router/__tests__/
├── composables/__tests__/
└── components/**/__tests__/
```

**`setup.ts` 要点：**
- 注册 Element Plus（组件测试需要）
- polyfill `ResizeObserver`、`IntersectionObserver`（Element Plus 依赖，jsdom 无）
- mock `window.matchMedia`
- 每个用例前 `sessionStorage.clear()` + `localStorage.clear()`
- MSW `server.listen()` / `resetHandlers()` / `close()`

## 八、建议修复优先级（供开发参考）

**P1**
1. **`Idempotency-Key` 改为按业务语义生成**（如 `订单号+操作类型`），当前实现防不住任何重复提交（F-R1）
2. 统一 401 与业务码 20001 的下线路径，都带 redirect（F-A5）

4. 结算页金额与后端对齐：前端只做展示，**最终以后端返回为准**，避免两套计算（F-M1/F-M2）

**P2**

5. 统一 `UserRole` 类型定义，消除 `types/common.ts` 与 `stores/user.ts` 的分歧（F-A4）
6. 守卫改为调用 `useDeviceGuard.checkDevice()`，消除重复实现（F-G3）
7. 关键写操作补前端防抖/按钮 loading 禁用（F-R2）
8. 评估 token 存 sessionStorage 是否符合预期，若需跨标签页则改 localStorage + 过期控制（F-A1）
