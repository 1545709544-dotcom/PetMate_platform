## 一句话介绍

**PetMate 是一个让宠物主在一个平台内完成「买用品、约服务、聊健康、晒日常、找领养」的宠物综合服务系统**，包含用户端、商家端、平台管理后台三个子系统，共享同一套后端 API 与数据库。

## 一、项目定位：解决什么问题

养宠家庭的日常事务分散在电商 App、宠物医院小程序、社区群和领养帖子之间——信息割裂、履约不透明、健康记录无处沉淀。PetMate 用一套账号体系把这五件事缝合到一起。

| # | 痛点 | 解法 |
| :-: | :--- | :--- |
| 01 | 买粮、约洗护、找医院要开三个 App，账号与优惠券互不相通 | 统一账号 + 统一订单中心，商品与服务共用购物车、优惠券与售后 |
| 02 | 宠物健康记录靠纸质本子，疫苗驱虫到期无人提醒 | 宠物档案 + 健康时间线，到期自动生成站内提醒 |
| 03 | 宠物不舒服时不知道要不要去医院，网上信息互相矛盾 | AI 智能问诊给出「紧急 / 建议就医 / 日常照护」分级建议并解释依据 |
| 04 | 寄养与上门服务价格不透明、无实景、纠纷难追溯 | 服务规格透明化（体型 × 毛长分档计价）+ 评价回复闭环 + 全流程留痕 |
| 05 | 领养信息散落在微信群，无审核无协议无回访 | 领养信息平台审核 + 申请状态流转 + 领养后回访，形成可追溯闭环 |
| 06 | 门店有服务能力但缺线上经营工具，排班库存全靠手工 | 商家工作台提供经营看板、订单履约、服务与评价管理 |

### 关于技术边界，我选择说清楚

Spring Boot、Vue3、JWT 这些框架的底层原理**不是我的强项**，我不会把它们写成简历上的「精通」。

我能做到的是：讲清每个业务模块的设计取舍、每个状态机的流转规则、每个边界情况为什么这样处理，并且**现场演示出来**。如果你需要的是能独立设计业务系统、把需求落成可用产品、并能对客户讲清楚产品价值的人，这个项目可以证明我具备这个能力。

## 六、功能全景与设计亮点

### 六个值得展开讲的点

| 功能 | 设计说明 |
| :--- | :--- |
| **AI 智能问诊** | 接入智谱 GLM-4-Flash 真实大模型，SSE 流式输出。输出分三级：紧急 / 建议就医 / 日常照护，并解释判断依据。无法确诊时明确提示就医，不给误导性结论，带每日配额控制。 |
| **售后 11 态状态机** | 售后不是简单的「申请—同意」，而是 11 个状态、三条角色分支（用户 / 商家 / 平台仲裁）的完整状态机，每次流转写入日志表，可追溯每一步由谁在什么时候操作。 |
| **限时秒杀** | 库存扣减用 CAS 原子更新（带库存充足条件），配合每人限购 1 件。下单失败或订单超时未支付时，回补秒杀名额、SKU 库存、优惠券与积分，不会超卖或库存泄漏。 |
| **鱼干积分体系** | 签到、评价、发帖等任务产出鱼干，每日上限 50。10 鱼干抵 1 元，单笔订单抵扣封顶 10%。积分流水可追溯，任务防重复。 |
| **领养救助闭环** | 送养发布（逐张图片上传、即时预览、失败可单张重试）→ 平台审核 → 用户申请 → 状态流转 → 领养后回访。送养人只能管理自己发布的信息，越权被服务端拦截。 |

## 九、面试高频问题 · 应答要点

<details>
<summary><b>Q1. 这个项目是你自己做的吗？你具体做了哪部分？</b></summary>

这个项目从产品定义到上线级交付是我独立完成的。需求拆解、模块划分、数据建模、业务规则与状态机设计、原型设计、验收自查、演示讲解由我主导；编码实现环节借助 AI 编程工具完成，我负责定义需求、判断产出是否符合预期、发现问题并推动修复。

**然后立刻给出证据**：我能具体讲清楚每个模块为什么这么设计。比如售后为什么是 11 个状态而不是简单的「申请—同意」，因为涉及用户、商家、平台三方，平台仲裁必须是一个独立环节，否则商家拒绝后用户没有救济路径。
</details>

<details>
<summary><b>Q2. 你用了哪些技术？熟悉到什么程度？</b></summary>

**不要吹。** 技术栈是 Vue3 + TypeScript + Element Plus 做前端，Spring Boot 3 + JDK 21 做后端，MySQL 8 存数据，AI 问诊接的是智谱 GLM-4-Flash。

但要**把话锋转到强项**：框架底层实现不是我的强项，我也不会把它写成精通。我的优势在于知道一个业务系统应该长什么样——数据怎么建模、状态怎么流转、边界情况在哪、用户在什么场景下会卡住。这个项目里 64 张表和 15 个业务模块的设计是我能完整讲清楚的部分。
</details>

<details>
<summary><b>Q3. 开发过程中遇到的最难的问题是什么？</b></summary>

挑一个**能讲出技术含量又不心虚**的：**秒杀和下单的库存扣减**。

最初的做法是「查出库存 → 判断够不够 → 更新库存」三步走，这个在并发下会超卖，因为判断和更新之间有间隙。后来改成一条 SQL 里带条件更新（库存大于购买数量才更新，用受影响行数判断是否成功），失败直接返回库存不足。同时处理了失败回补：下单失败或订单超时未支付时，要把秒杀名额、SKU 库存、用掉的优惠券、扣掉的积分都还回去，否则库存会「泄漏」。

这个例子好在它证明你理解「判断和操作之间的间隙」这个并发本质，而不只是背了个方案。
</details>

<details>
<summary><b>Q4. 如果让你重做，你会改进什么？</b></summary>

这题考的是反思能力，别说「没什么要改的」：

- **测试前置**：现在是功能做完才补测试，应该先把关键路径的验收用例写出来，边做边验
- **权限模型重做**：现在 RBAC 是演示态，真实项目应一开始就引入成熟鉴权框架，后期改造成本很高
- **支付与状态机解耦**：支付回调、订单状态、售后状态现在耦合较紧，应抽成独立的状态流转服务
- **加一层缓存**：商品详情和分类树读多写少，应加缓存降低数据库压力
</details>

<details>
<summary><b>Q5. 你觉得自己更适合什么岗位？</b></summary>

这个项目完整走了一遍「发现需求 → 设计方案 → 落地交付 → 验证效果」的循环，我觉得自己更擅长也更喜欢靠近业务和用户的那一端：理解真实场景里的痛点、把需求翻译成可执行的方案、把产品讲清楚并演示出来。

所以售前、技术支持、产品这类需要**既懂业务逻辑又能对外讲清楚**的岗位会更适合我。这个作品集就是我的证据——它不只是代码，是一套能讲、能演示、能回答追问的完整方案。
</details>

<details>
<summary><b>Q6. 这个系统能跑起来吗？现在能演示吗？</b></summary>

能，而且准备了两种演示方式：

- **方式一 · 真实系统**：MySQL + 后端 + 前端三层拉起来，用三个演示账号分别登录用户端、商家端和管理端，走完整流程
- **方式二 · 离线兜底**：这份作品集和原型演示站都是单文件 HTML，不依赖网络，断网也能翻着讲

另外准备了 26 个高保真原型，每个都标注了它对应到哪个真实页面，可以对照着看设计意图和最终实现的差别。
</details>
